# Linux 运行与性能决策

## 结论

现阶段没有测量证据支持重写战斗引擎或开发 GPU 模拟器。原游戏通过 Wine 已能完成状态读取、双方输入和规则策略对战。应先完善训练环境的重置、观测、奖励和终止条件，再开展 RL 研究。

不能把现有仓库直接当作已经完成的训练环境。当前有两个明确瓶颈：逐帧控制中的等待方式，以及每次重开都重新启动游戏。前者可以在 Python 控制端避免；后者需要实现并验证局内重置，或先接受进程重启的成本。

## 测量环境与口径

2026-09-29，双路 AMD EPYC 7302，32 个物理核心、64 个逻辑处理器，251 GiB 内存；Ubuntu 20.04、Wine 10.0 的 WoW64 构建、Windows Python 3.11.15、psutil 7.2.2。游戏和 DLL 使用现有的 x86 构建，桥接 ABI 为 6，没有修改战斗实现。

Xvfb 提供虚拟显示，使用软件图形驱动，每个软件渲染器限制一个线程。运行时游戏文件和 Python 基础解释器放在内存文件系统，避免网络盘读取影响启动和运行。没有运行神经网络或占用训练 GPU。

本文的一步是一个游戏实例同时接受双方输入，并完成一个战斗模拟帧。它不因有两个玩家而算作两步。每秒帧数表示真实时间内的模拟吞吐，不是窗口刷新率。

## 控制方式的影响

使用固定种子和同一条 3,000 帧动作序列，每种方式运行三轮。动作包含移动、跳跃与攻击。每步核对帧号、完成状态、实例间状态哈希，并读取帧记录。三轮之间重启游戏。

| 单实例控制方式 | 三轮计算阶段的步数/秒 |
| --- | ---: |
| 现有 `wait_for_ack()`，未完成时休眠 | 99–114 |
| 连续读取完整快照，取消显式休眠 | 1,140–1,610 |
| 先检查完成标记，完成后复制快照 | 5,463–5,984 |

最后一种方式由 `tools/interaction_benchmark.py` 的 `ready` 模式实现。它没有修改共享内存 ABI 或游戏计算逻辑。完整快照内部遇到写入竞争时会休眠，因而仅删除外部休眠还不能消除所有等待。

这些是三次完整轨迹的结果，不是长时间训练的速度保证。不同运行的进程启动耗时存在波动，不能用单次启动时间作确定性常数。

## 多实例结果

所有实例使用一个 Python 控制进程同步发动作；这不是多个独立采样进程的扩展测试。每档运行三轮，每个实例每轮 3,000 帧。

| 实例数 | 计算阶段总步数/秒 | 每次整批重开的实测耗时 | 计入两次重开后的步数/秒 |
| --- | ---: | ---: | ---: |
| 1 | 5,463–5,984 | 18.91–24.94 秒 | 198 |
| 8 | 25,238–25,843 | 31.93–32.46 秒 | 1,071 |
| 16 | 29,061–30,106 | 51.57–54.56 秒 | 1,297 |
| 32 | 启动失败，未测得有效吞吐 | 未完成 | 不适用 |

最后一列不含首次启动和最终退出。把首次启动也计入，1、8、16 实例分别为 148、670、895 步/秒，仍未计最终退出。必须明确这些边界，不能把纯计算吞吐当作完整训练吞吐。

1、8、16 实例的全部帧哈希在实例之间以及三次重开之间一致，丢帧为零。轨迹最终哈希为 `29540119E5823FD6`，与此前 Windows 验证轨迹的最终哈希一致。这不构成所有角色、所有动作和所有内部状态均一致的证明。

32 实例三次启动尝试均失败。Wine 报告 `d3d9.dll` 初始化发生 `c0000005` 访问异常。提高本任务进程的文件描述符上限到 65,536 后仍失败，根因尚未查清。不能据此断言服务器最多只能运行 16 个游戏，也不能承诺 32 实例可用。当前建议以已经验证的 8 或 16 实例开始。

另一次单实例连续运行测得 6,182 帧/秒，但记录队列丢失 35,805 帧。该结果只说明游戏可以快速推进，不能作为有效采样速度。

## 接入实际策略后的结果

三个状态决策树策略与静止对照完成三十六个单回合，共 113,405 帧，零丢帧，没有对象观测溢出。每个种子同时启动十二个配对实例，结束的回合停止采样，因此实际活跃实例数随击倒结果下降。

包含双方策略决策、状态转换、命令交互、帧记录和胜负判断的计算阶段吞吐为 9,216–9,461 帧/秒。每批启动耗时为 42.22–45.87 秒。规则策略没有神经网络推理成本，不能把这个速度直接用于 NFSP 或 PSRO 的训练时间估计。完整策略与对局结果见[基线说明](baselines.md)。

## 下一步施工顺序

1. **统一环境接口。** 把启动、双方步进、完整状态读取、超时和关闭集中到可调用的运行模块，复用完成标记的等待方式。当前基线运行程序仍复用了工具目录中的桥接代码。
2. **实现可靠重置。** 当前 `GotoFrame` 明确返回不支持；修改生命值和位置不能代替完整重置。实现局内重新加载后，要验证同一种子与动作序列下所有已观测帧一致，并测量重置耗时。
3. **定义学习问题。** 固定角色范围、状态可见范围、动作频率、单回合或整场的结束条件、奖励和超时处理。基线当前按首次击倒结束，不能默认为游戏完整赛制。
4. **接入第一种学习算法。** 用三个固定策略作训练与评估对手，记录真实神经网络推理、环境采样、重置和参数更新的各段耗时。先验证学习有效，再增加 NFSP 的策略平均或 PSRO 的对手集合。
5. **按测量决定后续优化。** 先测多个控制进程能否突破当前单控制进程的吞吐上限，再评估批量动作、精简观测、关闭不需要的历史记录。只有真实训练持续受战斗计算限制，且这些改动仍不能达到样本预算时，才评估独立模拟器。

Linux 与此前 Windows 测试使用不同 CPU，不能用两者帧率之比计算 Wine 的性能损耗。要回答这个问题，需要在同一台硬件上运行相同负载。

原始实验 JSON 保存在运行工作区的 `logs/validation`；它们是实验输出，不提交到 Git。启动与交互基准源码已提交，可以复测。
