# 后续开发计划

## 当前目标

先证明人类可以操作真实游戏，并证明程序能通过接口控制双方输入、读取状态和完成对战。当前验收不要求训练策略，也不要求部署强化学习训练任务。

单元测试、DLL 编译成功和真实游戏验收是三种不同证据。前两项通过后，仍需完成第三项。

## 第一阶段：可复现安装

补齐游戏本体、固定的第三方源码版本、x86 编译环境和模块配置。保留原始游戏文件，部署时列明新增文件与覆盖文件。

交付内容：

- Python 依赖声明与本地隔离环境。
- SokuMods 和 SokuLib 的固定提交号与获取步骤。
- Win32 桥接构建命令，以及 SWRSToys 模块部署清单。
- 安装检查：游戏版本、文件哈希、DLL 位数、配置存在、共享内存 ABI。

通过条件：新检出按文档安装后能进入 `PRACTICE_READY` 和 `VS_READY`。失败必须说明缺少哪个组件，不能把占位脚本的零退出码当作通过。

## 第二阶段：人类操作与自动接口验收

先启动一个有画面的实例，避免在资源有限的机器上直接启动并发基准。

人类操作验收：进入对战，用真实键盘或手柄完成移动、跳跃和攻击；核对角色、按键映射和窗口显示。程序接管后再释放输入，确认人类可以继续操作且游戏没有停在暂停状态。

自动接口验收：运行现有完整 VS 验证流程，证明双方动作变化、弹幕产生和 HP 减少；逐帧模式要求一次命令对应一个模拟帧，命令确认和结果码均正确。记录 PID、版本、帧号、结果和异常。关闭程序只影响本次启动的实例。

随后执行现有完整帧重建、场景与回放验收；回放验收需要有效的回放文件。最后执行正常与加速模式的完整一致性比较。只有在目标机器获得一致性证据后才使用加速模式开展后续工作。

通过条件：人类实际操作记录和程序真实对战报告均存在；完整记录的丢帧计数为零；没有遗留本次启动的进程。

## 第三阶段：整理可调用的运行接口

将 `BridgeClient`、进程生命周期和检查点重建移入 `src/soku_rl`，让命令行、调试窗口和验收脚本调用同一套实现。每次迁移保留行为并独立提交，避免同时重写协议和运行逻辑。

接口应覆盖启动、连接、读取、暂停、双方单帧输入、恢复、释放和关闭。明确超时、无效场景、游戏退出、ABI 不匹配和记录溢出的异常。确认等待应在超时后报错，不能让调用方误以为命令成功。

原生模块按协议、状态采集、输入与帧控制、启动与重建职责拆分；保持内存布局和接入地址不变。先移出独立职责，再决定是否需要更换协议定义方式。

通过条件：现有完整验收继续通过，运行模块不再导入验收脚本，安装包提供真正可调用的接口。

## 第四阶段：明确人机对战模式

在需要实时人机对战时，实现每位玩家的控制归属：人类使用原始设备输入，程序只覆盖指定玩家。定义程序退出、超时和异常时的释放行为。

先用固定规则控制器完成一次有画面的对战，再接入学习策略。固定规则控制器是按明确条件选择动作的程序，不需要训练模型。

通过条件：人类与程序各控制一方，双方输入互不覆盖；程序断开后可以恢复人工操作。

## 第五阶段：强化学习环境

仅在前述接口稳定且明确需要训练时，实现观测转换、动作空间、重置、奖励和回合结束条件，再接入 Gymnasium。Gymnasium 是约定 `reset` 和 `step` 等调用方式的强化学习环境接口。

先定义角色范围、可见信息、动作保持帧数、胜负和超时规则，再选择训练方法。训练前验证固定种子下的重置与动作序列可复现；并发数以目标机器的完整记录能力决定。

## 近期施工顺序

Windows 人类操作、自动接口验收，以及 Linux 的 16 实例交互与三模式一致性验证已完成。三个状态决策树和静止对照已完成两次三十六回合对战，逐局结果一致。详见[基线说明](baselines.md)和[Linux 性能报告](linux-performance.md)。

双人博弈接口已定义观测、联合动作、终局奖励和截断条件；配对评估可输出策略胜率及收益上下界。两个社区规则子集提供了有记忆策略的实际接入示例。详见[双人博弈与评估](strategy-evaluation.md)及[社区规则来源](community-ai.md)。

下一步将启动、同步和进程管理从验收脚本中独立出来，并实现可靠的局内重置。当前原生模块拒绝恢复检查点，重启进程的成本使此前完整基线实验降至每秒 756 帧；只看战斗计算帧率会高估训练吞吐。随后连接学习策略、训练数据收集和模型检查点，保持同一套评估协议。完整神 AI 的接入另需补齐碰撞框、角色状态和 Lua API。现阶段不重写战斗引擎。
